## 2. 문제 정의

### 핵심 문제: "안 읽는 게 아니라, 이해가 안 되는 것"

문화체육관광부 「2023년 국민독서실태조사」에 따르면 학생 종합독서율 95.8%, 종합독서량 36.0권(2021년 대비 1.6권 증가). 학생들이 책을 안 읽는 것은 아니다. 문제는 문해력, 즉 읽은 내용을 실제로 이해하는 능력의 하락이다.

### 근거 데이터

| 지표 | 내용 | 출처 |
|---|---|---|
| 학업성취도평가 (중3 국어, 보통학력 이상) | 2019년 82.9% → 2020년 75.4% → 2022년 63.4% → 2023년 61.2% → 2024년 66.7%. 코로나19 이후 급락, 회복 중이나 2019년 대비 16%p 낮음 | 교육부 국가수준 학업성취도평가 (2025.7 발표) |
| 교사 인식 조사 | 교사의 91.8~92%가 "학생 문해력이 과거보다 나빠졌다"고 응답 | 한국교원단체총연합회 등 설문 |
| 학생 독서량 | 종합독서량 36.0권, 종합독서율 95.8% — 2021년 대비 소폭 증가 | 문화체육관광부 2023 국민독서실태조사 |

> **해석:** 독서량과 독해력은 별개 지표다. 읽는 양은 유지·증가하는데 이해도와 현장 체감이 동시에 나쁘다는 것은, '더 읽게 만드는' 서비스보다 '제대로 읽었는지 검증하는' 서비스가 본질에 더 부합함을 시사한다.

> **개입 시점:** 위 통계는 중3 기준이지만, 독해 습관이 굳기 전인 초등 단계에서 개입하는 것이 효과가 크다. 따라서 타겟은 초1~중3으로 설정하고, 게임화 요소는 저학년 몰입도에 맞춰 설계한다.

**원인으로 지목되는 요인**

- 스마트폰·숏폼 소비 증가로 긴 글 사고 훈련 기회 감소
- 암기·객관식 위주 학습 문화
- 기존 완독 체크·사진 인증 방식이 실제 이해 여부를 검증하지 못함

## 3. 솔루션 개요

### 3-1. 레퍼런스: Pizza Hut BOOK IT!

1984년 시작한 독서 리워드 프로그램. 1985년 전국 확대 첫 달 23만 개 교실·700만 명 참여, 2017년 기준 누적 1,400만 명 이상 참여. 1999년 연구에서 외적 보상(피자)이 독서 습관에 부정적 영향을 주지 않았다는 결과도 있다. 2026년 현재도 앱 기반으로 운영 중.

다만 '완료 여부'만 신뢰 기반으로 확인할 뿐 실제 이해도는 검증하지 않는다는 한계가 있다. 본 서비스는 이 빈틈을 AI로 메운다. 서비스명 '책잇(Bookit)' 또한 이 레퍼런스에서 출발했다.

### 3-2. 플랫폼 형태

네이티브 앱스토어 정식 출시는 대회 일정상 불가능하다 (구글 14일 폐쇄테스트, 애플 키즈 카테고리 2~4주 심사). 대회 제출 요건이 '배포된 서비스 링크'이므로 **웹(PWA) 우선**으로 개발한다. 반응형 웹 + PWA로 홈 화면 아이콘을 추가해 앱처럼 실행되게 하고, 네이티브 출시는 로드맵으로 이관한다.

### 3-3. 핵심 플로우

1. 책 선택 (추천 또는 검색)
2. 독후감 작성 — AI 글쓰기 도우미가 가이드 질문 선제시
3. AI가 독후감을 책 내용과 대조해 논리적 빈틈 탐지
4. 빈틈을 짚는 해석·근거형 꼬리질문 1개 실시간 생성
5. 제한 시간 내 답변 → AI가 정합성·구체성 채점
6. 통과 시 책갈피 적립 → 도서관 무료 열람 또는 알라딘 구매 연결

## 4. 핵심 기능 상세

### 4-1. AI 이해도 검증 로직 (핵심 차별점)

질문은 '책 내용 일반'이 아니라 **'학생이 직접 쓴 독후감 문장'**에 고정한다. 유명한 책은 줄거리를 몰라도 그럴듯하게 답할 수 있어, 학생 본인 문장을 인용해 되묻는 방식이 대필·부정행위에 가장 강하다.

| 질문 유형 | 설계 원칙 | 채택 여부 |
|---|---|---|
| 해석·근거형 | 학생이 쓴 문장을 인용해 "왜 그렇게 생각했는지" 되묻기. 즉석 논리 전개가 필요해 대필 대응이 어려움 | **채택** |
| 디테일 확인형 | 등장인물 이름 등 지엽적 사실 질문 | 제외 — 실제로 읽었어도 잊는 경우가 많아 억울한 오탈락 위험 |
| 가정형 | "만약 ~라면?" 식 질문 | 제외 — 정답 폭이 너무 넓어 채점 기준 수립이 어려움 |

**빈틈 유형 3종** (목업에서 확정)

- 근거 없이 단정 — 판단을 말하지만 어느 장면이 근거인지 없음
- 뭉뚱그린 문장 — "여러 사건이 있었다"처럼 무엇인지 특정되지 않음
- 감상만 남음 — "감동적이었다"처럼 인물·장면과의 연결이 없음

**부정행위 방지 장치**

- 질문은 매 제출마다 실시간 생성 — 사전 유출 불가
- 답변 제한 시간 30초~1분 — 다른 AI 창을 열어 대응할 시간 차단
- 채점은 정답 여부가 아니라 독후감과의 논리적 정합성, 구체성, 문체 급변 여부를 보는 체크리스트 방식
- 재작성 시에는 다른 빈틈에서 새 질문을 생성

### 4-2. 도서 추천 — 장르 인접 확장

완전히 낯선 장르로 급전환하면 이탈 위험이 커진다. 사용자가 읽은 책의 태그를 누적 집계하고, 태그 대부분이 겹치되 1~2개만 새로운 책을 우선 노출한다. 추천 이유는 "평소 좋아하는 성장소설에 SF가 살짝 섞였어요"처럼 태그로 명시한다.

### 4-3. 리워드(책갈피) 시스템

- 실제 쿠폰 대신 자체 포인트 '책갈피'로 적립 — 외부 API 의존이 없어 심사 기간 안정성에 유리
- 검증 통과 1건 = 50 책갈피. 미통과는 기록만 남기고 0
- 국회도서관 전자책 열람권 300, 오디오북 열람권 450으로 소비
- 알라딘 구매 링크 제공 — 제휴 수수료 약 3% 내외 (요율 재확인 필요)
- 학년대에 따라 콘텐츠 난이도·추천 필터링

### 4-4. 로그인 및 계정 역할

구글 로그인 단일 적용(Supabase Auth). 만 13세 미만 계정은 구글 자체 보호자 인증을 거치므로 별도 연령 검증 부담이 줄어든다.

로그인 후 온보딩에서 **학생과 교사가 갈린다.**

- 학생: 학년(초1~중3) 선택 후, 교사에게 받은 6자리 반 코드를 입력해 반에 소속된다
- 교사: 학교·학년·반을 입력해 반을 만들면 6자리 참여 코드가 발급된다

학교·반 자유 입력은 쓰지 않는다. 아무나 "5학년 2반"이라고 입력하면 남의 반 아이들의 이해도 점수가 보이게 되기 때문이다.

학년 범위는 초1~중3으로 확정했다. 문해력 위기 통계가 중3 기준으로 논의되고, 게임화는 저학년일수록 몰입도가 높은 반면 고등학생은 입시 부담으로 실사용 가능성이 낮다고 판단했다.

### 4-5. 보호자 대시보드

별도 계정 체계 없이 '읽기 전용 공유 링크'로 구현한다. 기본 노출 항목은 완료 여부, 누적 책갈피, 이해도 점수, 읽은 책 목록이다. 나이스(NEIS) 학부모서비스 등 선례가 있어 법정대리인의 열람 자체는 개인정보보호법상 문제되지 않는다.

### 4-6. 교사 대시보드

교사가 자기 반의 진행 상황을 보는 데스크톱 전용 화면이다. 두 가지를 제공한다.

- **반 대항전 집계** — 반별 누적 책갈피와 검증 통과 건수, 우리 반 순위, 이번 주 기여도
- **우리 반 학생별 현황** — 학생별 통과 건수, 평균 이해도, 스트릭, 마지막 활동일

교사가 실제로 필요한 것은 두 번째다. 누가 뒤처지는지 봐야 독려할 수 있기 때문이다. 학교 단위 B2B 전환 스토리를 증명하는 화면이기도 해서, 심사 관점에서도 챌린지보다 우선순위가 높다.

**교사도 독후감 원문은 볼 수 없다.** 점수, 통과 여부, 완독 수까지다. 이유는 4-9와 같다.

### 4-7. 반·학교 대항전 (학생 화면)

반/학교 단위로 누적 책갈피와 통과 건수를 합산해 랭킹을 제공한다. AI 검증을 통과한 건수만 집계되므로 단순 인증샷 챌린지보다 신뢰도 있는 지표다.

**개인 순위가 아니라 반 대 반으로만 노출한다.** 특정 학생이 낮은 순위로 드러나 학부모 항의로 이어지는 위험을 줄이기 위해서다. 챌린지 화면의 협력형 반 목표도 같은 이유로 경쟁이 아닌 협력 구조다.

### 4-8. 책잇 서재 — 공개저작물 리더 + 단어 클릭 사전

최신 저작권 도서는 외부 전용 뷰어로 열람하므로 커스텀 기능을 심을 수 없다. 저작권 보호기간이 만료된 공개저작물(전래동화, 고전문학)에 한해 자체 리더를 구축한다.

국립중앙도서관 저작권 만료 디지털화 원문 중 3~5권을 선정해 텍스트로 렌더링하고, 단어를 누르면 국립국어원 한국어기초사전 Open API로 뜻풀이를 즉시 띄운다. 원문을 그대로 옮기지 않고 아이 눈높이에 맞게 각색해 사용한다.

### 4-9. 독후감 원문 비공개 원칙

독후감 원문은 **학생 본인만** 볼 수 있다. 교사도, 보호자도 볼 수 없으며, 학생이 특정 독후감을 직접 공개하기로 선택한 경우에만 열린다.

편의를 위한 결정이 아니라 서비스의 전제다. 아이가 감시받는다고 느끼면 방어적으로 쓰게 되고, 방어적으로 쓴 독후감에는 되물을 만한 빈틈이 없어 검증 자체가 무의미해진다.

| 나의 책나무·장르 도장판 | 완독마다 잎이 자라고, 장르별 3권 완독 시 도장 완성 | 중간 |
| 챌린지 | 반 협력 목표 + 시즌 한정 테마 | 중간 |
| 독서성향 리포트 | 누적 독후감 분석 요약 | 중간 — 시드 데이터 필요 |

## 5. 기술 스택

### 5-1. 확정 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 프론트엔드·백엔드 | Next.js (App Router, TypeScript) | 화면과 API를 한 저장소에서 관리 |
| 데이터베이스 | Supabase PostgreSQL | RLS로 역할별 데이터 격리 |
| 인증 | Supabase Auth (구글 OAuth) | 1일차 최우선 |
| 서버리스 | **Vercel Route Handler로 통일** | Supabase Edge Functions 미사용 |
| LLM | **1일차에 1개 벤더로 확정** | 제출 서류에 모델명 정확히 기재 |
| 배포 | Vercel | 프리뷰 배포를 통합 검증에 활용 |
| 스토리지 | 사용하지 않음 | 표지는 알라딘 이미지 URL, 원문은 DB 텍스트 |

### 5-2. 스택 관련 설계 결정

**서버리스는 Route Handler 하나로 통일한다.** Edge Functions는 Deno 런타임과 별도 배포 파이프라인이 추가되는데, 이번 범위에 DB 트리거 기반 백그라운드 작업이 없어 얻을 것이 없다.

**LLM 벤더는 하나로 고정한다.** 모델명을 제출 서류에 적어야 하고, 두 벤더에 프롬프트를 각각 튜닝할 여유가 없다.

**Storage는 쓰지 않는다.** 아이가 파일을 올리는 기능이 없으므로, 업로드 경로를 만들지 않는 편이 미성년자 서비스 안전 측면에서도 낫다.

**RLS는 처음부터 켠다.** 나중에 켜면 이미 작성한 쿼리가 전부 깨진다. 테이블을 만드는 마이그레이션에서 정책까지 함께 작성한다. 학생·교사·보호자 링크 세 종류의 정책이 필요하다.

### 5-3. 기술적 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 서버리스 함수 타임아웃 | 스트리밍 응답, 출력 토큰 상한, 심사 전 유료 전환 |
| 검증 화면 체감 지연 | 질문은 독후감 제출 직후 선행 생성, 타이머는 질문이 뜬 뒤 시작 |
| Supabase 프로젝트 일시정지 | 유료 전환 또는 주기적 핑, 심사 기간 매일 접속 확인 |
| API 키 유출 | 키는 서버 환경변수에만, LLM 호출은 인증 세션 뒤에서만 |
| 채점 기준 편차 | 통과 임계값을 환경변수로 분리해 시연 직전까지 조정 |
| 타이머 우회 | asked_at·answered_at을 서버 기준으로 기록, 클라이언트 카운트다운은 표시용 |

## 8. 비즈니스 모델

1. **파일럿** — 지자체·교육청 독서진흥 예산. 기존 예산 라인에 AI 검증이라는 차별점을 얹어 제안
2. **서점·출판사 제휴** — 알라딘 구매 연결 수수료 약 3% 내외
3. **브랜드 협찬** — BOOK IT! 모델처럼 청소년 고객 유입을 원하는 브랜드 쿠폰
4. **B2B SaaS** — 학교·학원 대상 라이선스. 교사 대시보드와 반 대항전이 도입 유인
5. **학부모 구독** — 상세 리포트

**광고 대신 제휴 추천.** 미성년자 대상 행동 기반 맞춤형 광고는 주요 플랫폼이 만 18세(네이버 14세) 미만에 대해 제한하고, 개인정보보호위원회 「아동·청소년 개인정보보호 가이드라인」(2022.7)도 최소화를 명시한다. 학년대 기반 콘텐츠 필터링과 제휴 추천도서 노출로 대체한다.

## 9. 비용 분석

독후감 1건 처리(4단계 AI 호출) 기준 입력 약 3,300토큰·출력 약 900토큰.

| 단계 | 시점 | 사용자 | 월간 처리 | AI + 서버 (월, 약) |
|---|---|---|---|---|
| 초기 | 출시~3개월 | 1,000명 | 30,000건 | 12.5만~41만원 |
| 중기 | 6개월~1년 | 30,000명 | 300,000건 | 99만~390만원 |
| 후기 | 1~2년 | 100,000명 이상 | 800,000건 | 284만~1,180만원 |

초기는 지자체 파일럿 예산으로, 중기는 제휴 수수료(권당 300~450원) 누적과 예산 확대로 커버 가능하다. 후기는 B2B SaaS와 학부모 구독이 본격화되어야 하는 구간으로, 수익 모델 검증이 선결 과제다.

## 10. 안전·윤리·법적 고려사항

**미성년자 개인정보 보호.** 만 14세 미만 아동의 개인정보 수집 시 법정대리인 동의가 필수다. 데모 단계는 보호자 동의 체크박스로 간소화하고, 실서비스 전환 시 정식 동의 플로우를 추가한다.

**수집 최소화.** 학교·반은 랭킹과 교사 집계에만 사용한다. 파일 업로드 경로를 두지 않는다. 독후감 원문은 교사·보호자 모두에게 비공개다(4-9).

**정서적 위기 신호 대응 — 현 단계 미구현.** 독후감의 정서 분석 후 부모 알림 기능은 다음 이유로 만들지 않는다.

1. 책 내용 자체가 슬프거나 무거운 경우가 많아 오탐 위험이 크다
2. 아이가 감시당한다고 느끼면 솔직한 글쓰기가 위축된다
3. 정서적 어려움의 원인이 가정 내 문제일 경우, 무조건적 부모 알림이 오히려 위험할 수 있다

향후 도입 시에는 명백하고 좁은 범위의 신호만 감지하고, 부모 알림보다 먼저 학생 본인에게 지지 메시지와 전문 상담 채널(109 자살예방상담전화, 1388 청소년전화)을 안내하는 방식으로 설계한다.

## 11. 개발 계획

### 11-1. 역할 분담 원칙

프론트·백엔드를 가로로 자르지 않고 **화면 단위로 세로로 자른다.** 각자 자기 화면의 UI와 API를 함께 소유하면 남의 작업을 기다릴 일이 줄고, 머지 충돌도 파일 단위로 갈린다.

단, 스키마·RLS·API 계약과 `src/shared/`는 김민경 한 명이 소유한다. 5명이 각자 Claude Code로 병렬 작업할 때 무너지는 지점은 속도가 아니라 '합'이다.

### 11-2. 담당별 범위

| 담당 | 모듈 | 맡은 것 |
|---|---|---|
| **강민구** | `ai`, `reader` | AI 프롬프트 4종, 장르 태그 정규화, 채점 품질 튜닝, 책잇 서재와 단어 사전 |
| **김민경** | `auth`, `teacher`, `shared` | DB 스키마·RLS·API 계약, 구글 로그인, 역할 분기, 반 코드, 교사 대시보드, PWA, 배포와 통합 |
| **이승환** | `books` | 도서 API 연동, 검색, 장르 인접 추천, 국회도서관 이동 |
| **박재경** | `review`, `verification` | 독후감 에디터와 자동저장, 빈틈 분석 화면, 타이머 질문, 채점 결과와 재작성 |
| **문민재** | `rewards`, `growth`, `ranking`, `guardian` | 책갈피 원장, 열람권 교환, 스트릭, 책나무·도장판, 반 대항전, 챌린지, 보호자 링크 |

**배치 의도**

- 강민구에게 리더를 붙인 이유: DB와 무관한 독립 모듈이라 프롬프트 결과를 기다리는 시간에 작업할 수 있고 통합에서 깨질 일이 없다
- 김민경은 코드를 가장 적게 쓰는 대신 통합 책임자다. 심사 기간 내내 링크가 살아 있어야 하므로 사실상 가장 중요한 자리다. 교사 대시보드를 붙인 것도 인증·RLS 위에 얹히는 조회 화면이기 때문이다
- 강민구와 박재경은 하루에 몇 번씩 붙어야 한다. 서비스의 유일한 차별점이 이 둘 사이에서 나온다
- 문민재는 모듈이 4개로 가장 많아 보이지만 책나무·챌린지는 로직이 적은 시각화다. 다만 랭킹 집계가 포인트 트랜잭션에 의존하므로 김민경과 스키마를 먼저 맞춰야 한다

### 11-3. 일정 (7일 집중 + 버퍼)

| 일차 | 작업 |
|---|---|
| 1일차 | 전원 스펙 합의 — 스키마·RLS·API 계약·LLM 모델 확정. 김민경이 당일 안에 빈 엔드포인트까지 배포. 구글 로그인 리다이렉트 URL 3종 등록 |
| 2~3일차 | 목 데이터로 병렬 구현. 강민구는 초등학생 수준 독후감 20건 테스트 세트로 채점 기준 확립 |
| 4일차 | 1차 통합. 여기서 안 붙는 기능은 잘라낸다 |
| 5~6일차 | 2차 통합, 실연동, 버그 수정. 시연 시나리오 리허설 최소 3회 |
| 7일차 | 배포 안정성 확인, 제출 |
| 이후 | 9.20까지 버퍼. 마감일 배포는 마감일에 터진다 |

확정한 `docs/spec.md`를 각자 Claude Code 세션 첫 프롬프트에 통째로 넣고 시작한다.

## 12. UI 설계

**브랜드 톤.** 크림색 줄노트 배경(`#FDF6EC`)에 코랄(`#FF6B4A`)과 노랑(`#FFD866`)을 포인트로 쓰는 노트·플래너 감성. 폰트는 Noto Sans KR. 리워드 명칭은 **책갈피**. 상세 토큰은 `docs/design-tokens.md`.

**검증 화면만 어둡다**(`#2B211B`). 다른 화면과의 대비로 "지금 검사받는 중"을 표시하는 의도된 선택이며, 톤을 맞추려고 밝게 바꾸지 않는다.

**반응형.** 768px에서 끊는다. 아래는 하단 탭 5개(홈·독후감·챌린지·나·서재), 위는 왼쪽 아이콘 레일과 2단 배치. 작성 화면의 좌우 분할과 서재의 사전 패널은 폰에서 각각 단계 전환과 하단 시트로 접는다. 교사 대시보드는 데스크톱 전용이라 모바일 레이아웃을 만들지 않는다.

**말투.** 아이에게 건네는 반말. 미통과 문구는 나무라지 않고 다음 행동을 제시한다("조금만 더!", "다시 답해볼까?").

### 공통 원칙

**표지 이미지.** 목업의 색상 블록은 전부 자리표시이며, 실제로는 알라딘 Open API의 표지 이미지가 들어간다.

**장르 태그.** 수동 태깅이 아니라 알라딘 카테고리(보조: KDC 분류)를 자동 수집한 뒤 AI가 앱이 쓰는 10~15개 태그로 정규화한다. 이 태그가 추천 알고리즘의 입력값이다.

**알라딘 구매 연동.** 알라딘 결제를 직접 대행할 공개 API는 없다. 책갈피를 도서문화상품권 코드로 전환해 지급하고, 학생이 알라딘 결제 시 직접 입력하는 구조로 설계한다. MVP에서는 팀이 소액 상품권을 미리 구매해 수동 지급하는 방식으로 검증한다.

| 포인트 명칭 '책갈피' | 서비스명과 어울리는 브랜드 일관성 |
| 학년 범위 초1~중3 | 문해력 통계, 게임화 적합성, 실사용 가능성 종합 고려 |
| 해석·근거형 질문만 채택 | 대필 대응이 어렵고 채점 기준을 세울 수 있는 유일한 유형 |
| 독후감 원문 전면 비공개 | 감시받는다고 느끼면 방어적으로 써서 검증 자체가 무의미해짐 |
| 반 코드 기반 소속 | 자유 입력은 남의 반 데이터 열람을 막을 수 없음 |
| 교사 대시보드 추가 | B2B 전환 스토리를 증명하는 화면. 챌린지보다 우선 |
| 개인 랭킹이 아닌 반 대 반 | 개인 순위 노출로 인한 학부모 항의 리스크 회피 |
| 도서관 무료 열람을 책갈피 교환에서 분리 | 무료 열람과 포인트 소비는 성격이 다른 행동 |
| 장르 태그 자동 수집 + AI 정규화 | 수동 태깅의 확장성 한계, AI 활용 사례 추가 |
| 알라딘 구매를 상품권 코드로 | 공식 구매대행 API 부재에 대한 현실적 대안 |
| 완독 카드를 채점 결과에 통합 | 카드 자체가 공유 가능한 완독 카드가 되어 화면 단순화 |
| 포인트 원장 방식 | 잔액 컬럼 없이 누적 합산 — 이중 지급과 정합성 오류 방지 |
| 서버리스를 Route Handler로 통일 | Edge Functions는 배포 파이프라인만 늘고 이점 없음 |
| LLM 벤더 단일화 | 모델명 기재 요건 + 프롬프트 튜닝 시간 확보 |
| Storage 미사용 | 업로드 경로를 만들지 않는 것이 미성년자 서비스 안전에 유리 |
| 화면 단위 세로 분할 | 5인 병렬 작업 시 대기 시간과 머지 충돌 최소화 |
